# ADR-004. Contract-first API: zod + ts-rest в `packages/contracts`

**Статус:** accepted, 2026-09-21

## Контекст
Фронт и бэк пишутся параллельно разными агентами. Нужна единственная точка правды по формам запросов/ответов, из которой одинаково получаются серверная валидация, типизированный клиент и моки.

## Решение
- Контракт описывается zod-схемами и ts-rest роутером в `packages/contracts`, по файлу на домен с одним BE-владельцем.
- Сервер: `@ts-rest/nest` реализует контракт; `ZodValidationPipe` валидирует вход.
- Клиент: `@ts-rest/react-query` — типизированные хуки.
- MSW-хендлеры пишутся против тех же схем и фикстур из `contracts/fixtures`.
- SSE-эндпоинты (ИИ) описываются zod-схемами событий и реализуются обычным контроллером.
- Ошибки — единый `ApiError`, коды в `contracts/errors.ts`.

tRPC отклонён (жёсткая связка с TS-клиентом, нет REST для вебхуков/внешних интеграций). Ручной OpenAPI отклонён (двойная работа, дрейф).

## Последствия
- Изменение контракта = осознанное действие владельца домена с уведомлением FE-потребителей.
- Из контракта можно сгенерировать OpenAPI для внешних клиентов.
- Если ts-rest перестанет поддерживаться — схемы zod остаются, меняется только клей.
